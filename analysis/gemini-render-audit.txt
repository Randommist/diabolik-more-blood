### 4. Delay Slots and Branch Likely (`bltzl`, `bnel`) Audit

MIPS **Branch Likely** specification:
- If the branch condition is **TRUE**, the instruction in the delay slot is executed.
- If the branch condition is **FALSE**, the instruction in the delay slot is **NULLIFIED** (treated as NOP).

Audit at every branch:
1. **`0005c670 bltzl $s0, 0x5c6a0`**
   - Delay slot: `0005c674 addu $a0, $a1, $a0`

#### Question: "Can geometry helper alone prove safe width for runtime width 480, height 472, x 0, y 4?"

**Conclusion: NO.**
1. **Unbounded String Length / Clipping Ignored**: The geometry helper only reads global bounding box parameters (`X, Y, W, H`) and outputs either centered origin or box dimensions (`*a2 = W`, `*a3 = H`). It contains **no bounds check, no string length inspection, no line-wrap logic, and no clamping**.
2. **Text Run Independence**: The text advance in `0005c644` increments `4($s1)` sequentially for each character without querying the geometry helper during each glyph's step.
3. **No Safety Proof**: Proving whether text fits safely within `width 480` requires knowing the total string length $N$ (total width $\approx N \times 11\text{ px}$ plus tracking/spacing) and comparing it against $480 - X$. The geometry helper alone only provides/stores the window/box extents; it does not validate or enforce that the rendered glyphs stay within 480 pixels. Drawing conclusions about "safe width" based solely on this helper is mathematically and architecturally unsupported.
